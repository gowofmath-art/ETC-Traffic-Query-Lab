# ETC Traffic Query Lab

> 一個以 Python、資料結構、演算法與系統設計為核心，從零打造的個人 ETC 車流查詢實驗平台。

---

## 專案簡介

**ETC Traffic Query Lab** 是一個由個人獨立設計與實作的 ETC 車流查詢平台。

本專案源自原先課程中的 ETC 車流查詢專題，但不直接延續原本的「單機 Kubernetes 架構」，而是重新從零設計一套能夠在個人電腦上執行的查詢系統。

本專案的目的，不是打造功能最多、資料集最龐大，或足以取代正式交通平台的系統，而是希望親自理解並完成整個系統中的重要環節，大致上可分為：

1. 資料擷取：使用爬蟲程式有系統地擷取原始資料。
2. 資料清洗：將原始資料作清洗。
3. 資料的後處理：設計資料結構存放資料。
4. 查詢邏輯：搭配資料結構，設計良好的查詢邏輯，必須要熟悉演算法。
5. 後端 API：串接前端網頁。
6. 前端網頁設計：設計網頁樣式與架構、以及功能互動。
7. 效能測試：針對自己設計的不同資料結構產生的不同方案，做為比對。

本專案中的每一個核心功能，最終都應該能回答以下三個問題：

1. 為什麼它是正確的？
2. 它是如何運作的？
3. 為什麼選擇這種設計？

---

## 專案目標

### 1. 從零建立完整查詢系統

本專案不以堆疊大量框架或工具為目標，而是希望透過實作，理解每個模組在系統中的功能與責任。

重要功能不應只是「能夠執行」，還必須能夠說明其內部邏輯、資料流向與設計理由。

---

### 2. 比較不同的查詢策略

本專案不只實作單一查詢方法，也會逐步比較不同方案，例如：

- CSV
- Parquet
- 不同的資料切分方式
- 不同的索引策略
- 不同的資料結構
- 不同的前處理方法

每一種方法都應同時從以下兩個角度分析：

- 理論上的時間複雜度與空間複雜度
- 實際執行時的效能測試結果

---

### 3. 驗證個人電腦是否足以執行

本專案希望研究：

> 在本專案採用的資料規模與查詢需求下，經過良好設計的單機系統，是否能以較低的系統複雜度，提供合理甚至更好的查詢效能？

本專案並不是要證明 Kubernetes、Hadoop 或 Spark 沒有價值，而是希望分析：

> 在目前這個具體問題與資料規模下，是否真的有必要引入這些複雜技術？

---

### 4. 透過實作展現工程能力

本專案重視的不只是最終網站畫面，而是整個開發過程中所展現的能力，包括：

- 軟體架構
- 模組化設計
- 可讀性
- 版本控制
- 測試
- 文件撰寫
- 實驗設計
- 效能分析
- 技術選擇與理由說明

## 專案核心原則

本專案遵循以下原則：

1. Python 是系統核心語言。
2. 正確性優先於效能。
3. 所有優化都必須有基準方案。
4. 每次實驗應盡量只改變一個主要變因。
5. 預處理成本與查詢成本應分開計算。
6. 不為了使用技術而使用技術。
7. 所有重要變更都使用 Git 與 GitHub 進行版本控制。
8. 所有核心功能都必須能被理解、解釋與重現。
9. 專案先完成最小可行版本，再逐步擴充。
10. 系統複雜度必須有明確理由。

## 使用資料集

為了控制專案範圍，第一階段只使用 TDCS 的兩種資料集：

1. M03A(各類車種通行量統計各類車種)：依車輛種類通過單一偵測站統計之交通量
2. M06A(各旅次路徑原始資料)：各旅次之完整行駛路徑資料，旅次係指一車輛自進入交流道到離開交流道稱為1個旅次

本專案暫時不加入其他資料集。

這並不是因為其他資料沒有價值，而是因為本專案重視的是對問題的深入研究，而不是資料來源的數量。

---

### M03A

M03A 屬於聚合型車流資料，可用於研究：

- 時間區間查詢
- 門架篩選
- 車種篩選
- 車流量統計
- 分組與聚合
- 儲存格式比較
- 分區策略
- 索引設計
- 排序與二分搜尋
- 預先計算與即時計算的差異

M03A 主要代表的問題是：

> 如何在大量統計資料中，快速找出符合時間、門架與車種條件的結果？

---

### M06A

M06A 屬於車輛旅次與軌跡資料，可用於研究：

- 起始與終點時間查詢
- 起始與終點門架查詢
- 車種篩選
- 車輛經過紀錄
- 門架順序
- 路段判斷
- 車輛去重
- 路徑查詢
- 圖結構
- 序列比對
- 倒排索引

M06A 主要代表的問題是：

> 如何根據時間、門架順序與車輛紀錄，有效率地判斷哪些車輛通過指定路段？

---

## 專案研究方向

本專案主要分成兩類研究問題。

### M03A：聚合型查詢

研究不同的：

- 儲存格式
- 分區方式
- 排序方式
- 索引策略
- 查詢引擎

如何影響查詢效能。

可能比較的方案包括：

```text
原始 CSV 線性掃描
清理後 CSV
Parquet
依日期分區
依門架分區
時間排序
二分搜尋
雜湊索引
```

---

### M06A：旅次與路徑查詢

研究如何利用：

- 車牌或車輛識別資訊
- 門架順序
- 時間資訊
- 路網結構
- 資料索引

快速判斷符合指定路段與時間條件的車輛。

可能比較的方案包括：

```text
完整線性掃描
依車輛分組
依門架建立索引
排序後進行序列判斷
倒排索引
門架圖結構
路徑查找
```

## 各資料夾用途

### `data/`

存放專案使用的資料。

#### `data/raw/`

存放原始資料。

原始資料原則上不可直接修改，任何清理、轉換或格式變更，都應輸出成新的檔案。

#### `data/sample/`

存放小型樣本資料。

用途包括：

- 快速開發
- 單元測試
- 功能展示
- GitHub 範例
- 讓其他使用者能快速重現部分功能

#### `data/metadata/`

存放輔助資料，例如：

- 門架名稱
- 門架座標
- 門架方向
- 門架順序
- 欄位定義
- 車種代碼
- 資料格式說明
- 對照表

#### `data/staging/`

暫時解壓縮區，處理完成後可以刪除。

---

### `src/`

存放正式系統程式碼。

#### `src/etc_query/core/`

存放核心邏輯，例如：

- 查詢條件模型
- 共用資料格式
- 查詢結果格式
- 介面定義
- 共用驗證邏輯
- 例外處理

#### `src/etc_query/engines/`

存放不同的查詢引擎。

例如：

```text
csv_engine.py
parquet_engine.py
indexed_engine.py
```

不同查詢引擎應盡量使用相同的輸入與輸出介面，才能進行公平比較。

#### `src/etc_query/preprocessing/`

存放資料前處理程式，例如：

- 欄位清理
- 資料格式轉換
- 缺失值處理
- CSV 轉 Parquet
- 建立分區資料
- 建立索引
- 建立樣本資料

#### `src/etc_query/structures/`

存放專案中自行設計或封裝的資料結構，例如：

- 雜湊索引
- 排序陣列
- 倒排索引
- 門架圖
- 路徑結構
- 時間索引

此資料夾會在實際需要時再加入。

---

### `experiments/`

存放實驗程式與效能比較結果。

每一個實驗應盡量包含：

- 實驗目的
- 使用資料
- 控制變因
- 測試方法
- 查詢次數
- 執行時間
- 記憶體使用量

- 結論

例如：

## Git 開發原則

目前以 `main` 作為主要分支。

初期的基礎建設可以直接在 `main` 上完成。

當專案已有穩定版本後，較大型或具有風險的功能可以建立短期分支，例如：

```text
feature/parquet-engine
feature/flask-api
experiment/time-index
experiment/gantry-graph
fix/time-range-boundary
```

完成、測試並確認無誤後，再合併回 `main`。

`main` 原則上應保持可執行、可測試與可展示。
